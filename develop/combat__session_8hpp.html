Detailed Description

Turn & action-economy orchestrator (universal mode).

The code review's gap was "no turn & action-economy orchestrator": the engine could tick one sheet's durations (RulesetEngine::runTurn) but there was no object that owns an order of combatants, tracks how many standard / bonus / reaction actions each has left this turn, and drives the per-combatant turn so round-based effects (poison lasting 3 rounds) decay automatically. This header closes that gap with CombatSession:

  1. an initiative queue (rolled from each combatant's Initiative stat plus a die, re-rolled each round),
  2. a per-turn ActionBudget (D&D-like 1 standard / 1 bonus / 1 reaction / movement points by default) enforced together with the existing RulesetEngine::actionAllowed restriction checks (a paralyzed combatant cannot spend an action), and
  3. CombatSession::runCurrentTurn, which calls the engine's RulesetEngine::runTurn for the acting combatant — firing OnTurnStart / OnTurnEnd, ticking durations, and firing recurring (ongoing) effects — so "poison deals 1d6 for 3 rounds" decays to nothing across three of that combatant's turns.
Why a separate orchestrator instead of changing the fight simulator?
combat.hpp's runFight is a self-contained Monte-Carlo simulator used by the ELO ranking; it intentionally consumes a scripted, deterministic RNG stream and must not gain extra dice (ticking, initiative re-rolls would perturb the stream and break thousands of scripted assertions). A CombatSession is the interactive counterpart: it owns initiative order and action economy for an application-driven combat where the caller decides what each combatant does, and the engine handles the bookkeeping.
Who owns the entities?
The session does not own entities — it stores EntityHandle s into a EntityRegistry (or GameSession). Removing an entity from the registry makes its handle expire; the session skips expired combatants, so a creature that dies mid-round simply stops taking turns.
